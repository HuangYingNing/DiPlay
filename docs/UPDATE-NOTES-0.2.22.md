# DiPlay 0.2.22 更新说明

- 合并原始项目 0.2.16 之后至 0.2.22 的源码更新，基础版本号同步为 `0.2.22`。
- 合入车机热点无线连接、Wi-Fi 音乐时钟、USB 语音录制、有线重连与连接失败诊断等上游修复。
- 合入更新下载校验、输入边界与诊断信息处理等上游安全修复。
- 保留本项目的吉利星愿车机适配、GD 车桥、ADB 诊断、PasteDB 日志上传和 HuangYingNing Release 更新通道。
- PasteDB API Key 仍由本地忽略文件或 GitHub Actions Secrets 注入构建；密文与解密密钥不得提交 Git。
- 发布版本继续使用 `v0.2.22-bYYMMDD-nnn` 格式；日志上传时附带源码 commit 号。
- 星愿“不支持”模式不再要求先从 Android 蓝牙清单选择 iPhone，允许进入 Flyme Auto 广播连接路径；若车机仍不向普通应用暴露设备，握手仍可能失败，诊断日志会记录该路径。
- 应用内热点凭据缺失时，先尝试从车机已保存的热点配置恢复；诊断报告只记录凭据是否存在，不记录密码。
- 星愿/Flyme Auto 的手动热点模式在 Android 将活动 Wi‑Fi 接口误报为上游网络时，允许该活动接口用于 CarPlay 广播，并记录 `flyme_wifi_upstream` 证据；其它车机仍要求热点接口归属证据。
- 星愿“不支持”模式在 Android 蓝牙清单没有 iPhone 时，不再用 `_carplay-ctrl._tcp` TXT 字段冒充蓝牙配对地址；该 TXT 服务依赖先完成蓝牙启动流程，不能作为可靠的 RFCOMM 目标来源。
- 星愿连接诊断增加绑定车机热点网卡的被动 mDNS 观测，分别统计本机和非本机来源的查询、响应及 CarPlay/AirPlay 服务标记，不记录数据包内容、设备名称或地址；同时在车机 ADB 已授权时只读采集系统蓝牙、Wi-Fi 服务和相关服务名状态。
- 2026-11-12 上传的车机日志显示 Android 公共蓝牙接口报告适配器关闭、配对设备和 ACL 连接数为零，未记录 ACL 连接事件；Bonjour 未发现 `_carplay-ctrl._tcp`，而原有 UDP 计数是设备级总量，无法证明来自 Wi-Fi 组播或 iPhone。新增被动观测用于下一份实车日志验证实际广播，不会主动扫描或切换车机蓝牙/Wi-Fi。
- 若新增日志中的 mDNS 观测无法加入组播组，或车机 ADB 状态为未授权，日志会明确标出权限/访问状态；Flyme Auto 的系统权限仍需用实车日志确认，不能仅凭热点已连接推定应用可读取其蓝牙设备或数据。
- 2026-11-12 v006 的最新实车日志显示 mDNS 监听已加入组播组，但 13 个观测包均来自本机、非本机包为 0；车机蓝牙接口仍报告关闭且没有 iPhone 目标，ADB 返回未授权，因此尚未执行车机系统服务查询。出现该状态时，连接失败改为提示在高级设置中请求并批准 DiPlay ADB 授权，并停止无效的自动重试；ADB 授权后仍需日志证明是否存在可用的 Flyme Auto 蓝牙接口，不能将此版本描述为已经恢复无线连接。
- 2026-11-12 v007 实车日志确认“允许 ADB”流程等待 60 秒后仍未获批，车机 `ADB_ENABLED=0`、DiPlay 没有 `WRITE_SECURE_SETTINGS`，本地 5555 端口虽开放但没有授权结果。新增超时后的开发者设置回退，避免只提示一个车机没有显示的授权弹窗。
- 最新日志中热点候选接口为 `eth0`，但 Android 热点接口清单未确认其属于 AP，系统把它标记为 Flyme Wi-Fi 上游；因此不能把接口存在等同于 iPhone 已连入该热点。后续需依靠车机授权后的只读网络/蓝牙系统诊断或 Flyme Link 官方 SDK 接口确认。
- Flyme Link 资料调研与适用范围见[调研记录](FLYME_LINK_RESEARCH-20261112.md)。目前官方公开接入文档没有发布 SDK API 细节，尚不能据此实现或验证 iPhone CarPlay 握手。
- 诊断页新增“导出系统包”：用户主动点击后，把可读取的 Flyme、吉利、蓝牙、Wi-Fi 等相关系统 APK、版本、路径和 SHA-256 保存为本地 ZIP，并可通过系统分享。普通应用无法读取受保护的 OTA 完整包；此版本用于采集证据，尚未确认修复 iPhone 握手。
- 诊断页新增“上传系统包”：点击后重新采集 ZIP 并上传至公开的 Filebin 临时文件服务，校验服务端 SHA-256；本地路径、下载链接、过期时间与失败原因写入诊断日志，便于随后通过 PasteDB 日志定位文件。持有链接的人可以下载，服务通常在约 7 天后删除；车机网络可达性仍须实车验证。
- 修复首次尚未启动 CarPlay 会话时日志目录不存在，导致系统包上传路径与下载链接静默丢失的问题；现在独立上传操作也会创建日志目录。
- 启动后仍由 WorkManager 约 2 分钟启动更新检查；该检查不受上一次成功检查的 24 小时间隔限制，检查失败时在后台按 20 秒间隔短期重试，之后交由现有自动任务退避机制处理。
- 更新 APK 在独立下载线程中运行，切换设置菜单不影响下载；失败后每 5 秒重试，保留已下载分片并通过 HTTP Range 续传，校验失败时清除损坏文件后重试。
- 2026-11-13 实车日志及系统包已在本机归档并校验：Android 蓝牙接口报告关闭、看不到已连接的 iPhone；所选 `eth0` 仅收到本机 mDNS 包，无法证明手机广播进入应用。诊断不再把 ADB 未授权直接写成连接失败原因，而是分别提示车机无线接口不可见；ADB 授权仅用于补充诊断。
- 用户主动导出系统包时，补收本次清单中可见但旧规则漏收的 Android Car、网络栈、系统设置及车机消息通道组件，供下一轮核实是否存在可访问的宿主接口。本次包没有蓝牙核心服务或 Flyme Link 主程序；尚未确认普通应用能完成 iPhone 的无线握手。
- 2026-11-13 的 v005 实车日志继续显示 Android 蓝牙关闭、`eth0` 只有本机 mDNS 包。新系统包已在本机校验，15 个 APK 成功收集；关键的 `com.reachauto.messagechannel` 因原有 256 MiB 总量限制被跳过。下一版将它排在采集首位，并把归档原始字节总上限提高到 384 MiB。
- 已取得的 `com.android.car` 中，投屏热点接口需要签名或特权级 `android.car.permission.CAR_PROJECTION`；吉利设置中心已使用消息通道，但目前见到的请求用于账户和车辆信息。新增只读日志检查消息通道服务是否对 DiPlay 可见、是否导出及权限状态，不主动绑定或请求账户数据。尚未取得消息通道服务端 APK，也未找到能使普通安装版读取车机宿主蓝牙或热点广播的接口。
- 系统包采集会优先补收消息通道等此前漏收组件，并对已成功上传、且摘要未变化的 APK 跳过重复采集。ZIP 的 `manifest.json` 列出应用可见的所有已安装 APK 的包名、路径、大小和系统应用标记，并记录不可读取目录数与是否触及 10 万文件上限；`system-files.txt` 保存可见系统分区的文件路径总表。清单不写入诊断日志，日志仅保存系统包上传状态、下载链接等定位信息。普通应用不能保证遍历受保护目录，不能把清单视为完整 OTA 文件表。
- 修正“上传系统包”运行中的按钮文案：上传系统包时显示“正在上传系统包…”，上传诊断日志时仍显示“正在上传日志…”。
- 2026-11-13 v006 实车日志仍显示 Android 蓝牙关闭、没有可见 iPhone，`eth0` 上 mDNS 非本机包为零。此次系统包已在本地校验，包含 25 个 APK 及 5,421 条应用可遍历的系统文件路径；消息通道服务可见且已导出，但已检查的服务端代码未发现提供 iPhone 蓝牙目标或原始 Wi-Fi 广播的接口。握手问题尚未证实得到解决。
- 深入核查新系统包后，应用可见的 155 个已安装包中未见 `com.android.bluetooth`，可遍历的系统路径中也未见蓝牙主应用 APK；这提示车机宿主蓝牙可能处在 DiPlay 不可见的环境，但文件清单不完整，不能据此断定架构。现有 Bonjour 已持有 Wi-Fi 组播锁，故不会把缺少组播锁当作已证实原因。无线诊断将在 8 秒观察结束时补记所选网卡的接收包、字节和丢包增量，并记录组播锁状态；未观察到手机 mDNS 包时不再推断整个热点流量不可读取。Apple 公开的无线 CarPlay 流程要求先完成蓝牙发现和凭据交换，再通过 Wi-Fi 通信；普通蓝牙列表看不到 iPhone 仍是当前握手前置阻断。
- 在支持 Android 原生卸载提示的车机上，卸载 DiPlay 时可选择“保留应用数据”，以便用相同包名和签名重新安装后继续使用原有热点名称及密码。若车机卸载程序不提供该选项或用户选择清除数据，本地私有设置仍会丢失；此功能并不等于云端自动备份。
- 星愿无线诊断增加吉利 OneOS 电话蓝牙服务的只读尝试：先确认服务可见且允许绑定，再查询车机蓝牙状态和当前设备是否存在，不记录设备名称或地址。当前系统包未见其服务端，故此项仅用于识别是否存在可授权的宿主桥接；即使能取得设备信息，仍需可读写 iAP2 RFCOMM 通道才能完成无线握手。
- 旧实车日志确认 `adb_enabled=0`、DiPlay 无权写入该设置，本地 5555 端口虽开放但公钥未获批准；“开发者设置”请求实际打开的是立刻关闭的禁用占位页。系统包另有可响应 `DEVICE_INFO_SETTINGS` 的设备信息页，内含连续点击版本号七次启用开发者选项的标准控制器，但要求管理员用户、已完成设备配置且未限制调试。现在遇到禁用占位页会改为打开设备信息，并补记这些条件及 TCP 调试端口属性，供实车判断是否能从系统设置正式启用调试。普通安装版不能自行批准 ADB 公钥。
- “检查 ADB 访问”和“允许 ADB”执行时保留原按钮并临时禁用，进度和结果分别显示在对应按钮正下方；信息行与按钮之间增加留白，运行中的提示改为黄色，不再出现在“车辆数据模式”下面。
- 再次核查 AOSP 与星愿系统包后，确认“开发者设置已禁用”占位页本身属于 Android 原生机制，不能单凭该页面判断 Flyme 修改了入口。“检查 ADB 访问”和“允许 ADB”新增 ADB 协议阶段、系统调试开关和属性、USB 状态、系统授权组件日志，返回设置页后也记录状态；仅记录包类型和组件状态，不记录公钥或授权指纹。对于只开放 TCP 端口而未回复 ADB 握手的服务，不再误报“待授权”。系统包新增收集公开的 `framework-res.apk`，以核对车机是否覆盖了 ADB 授权组件配置。仍需实车日志判断授权弹窗未出现的具体环节。

上游各项变更及其验证限制见 [原始项目 0.2.22 发布说明](RELEASE-NOTES-0.2.22.md) 和[验证记录](VALIDATION.md)。合并后的完整版本尚未在吉利星愿车机上完成实车验证，不代表已确认所有上游功能均与 Flyme Auto 兼容。
